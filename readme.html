Keel — Agentic SDLC Governance Framework

The structural backbone every delivery vessel needs. A technology-agnostic, deployable governance framework for AI-assisted software delivery.

Keel is a starter kit: a bundle of constitution documents, process definitions, machine-enforced guardrails, templates, and CI workflows that let any team run a disciplined, auditable, AI-assisted SDLC from day one — and tweak it to fit.

It was distilled from a production governance system (24 enforcement hooks, 6 session archetypes, a 22-rule constitution, ADR governance, and an autogenerated state-of-truth delivery plan) and generalized so it can be dropped into any repository, in any language, under any agentic coding tool.

Why this exists

AI coding agents are fast and tireless, but they have no institutional memory, no sense of "we already decided this," and a strong bias toward plausible-looking output. Left ungoverned they produce code that compiles, looks right, and quietly violates the constraints that actually matter: tenancy isolation, API stability, security posture, architectural boundaries.

Governance-by-documentation doesn't survive contact with a fast agent — nobody re-reads the standards doc on edit #400. Keel's premise is that the rules that matter must be mechanically enforced at the moment of action, not advisory. Everything else (process, templates, principles) exists to make that enforcement legible and tweakable.

Three layers, each usable on its own:

LayerWhat it isLives in
ConstitutionThe non-negotiables: inviolable rules, autonomy tiers, quality + security principles. Tool-neutral.core/constitution/
ProcessHow work flows: SDLC gate, session archetypes, task classification, ADR governance, review framework, knowledge capture. Tool-neutral.core/process/, core/governance/
EnforcementThe teeth: machine-checked guardrails that block non-compliant actions. Ships as a Claude Code adapter (hooks + skills + settings) and CI workflows.enforcement/, ci/

The constitution and process layers are pure documentation + templates — portable to any tool or no tool. The enforcement layer is where technology shows up; the default adapter targets Claude Code, and the patterns are documented so they can be re-homed to other agentic tools, git hooks, or CI.

The 30-second mental model

  1. Classify every piece of work (Feature / Bug / Debt / Security / Ops / Discussion). Classification decides which gates apply. → core/process/task-classification.md
  2. Gate the work before it starts: Features need a spec; fixes need a quick plan with impact analysis. → core/process/sdlc-gate.md
  3. Constrain the agent with inviolable rules + autonomy tiers. High-blast-radius changes (schema, auth, API contracts, cross-boundary) always escalate to a human. → core/constitution/
  4. Enforce mechanically. Hooks block edits that skip a spec, claim "done" without a delivery record, run two sessions in one checkout, or touch a frozen interface without review. → enforcement/
  5. Record every delivery (what changed, what was verified) and capture every non-obvious lesson as a knowledge note. → core/templates/, core/governance/knowledge-management.md
  6. Decide architecture in ADRs; review governance-recursive changes adversarially. → core/governance/

Quick start

# 1. Copy the framework next to (or into) your target repo, then:
cp framework.config.example.yaml framework.config.yaml
$EDITOR framework.config.yaml          # set org, project, stack, default branch, tiers

# 2. Dry-run the installer to see what it will write
bash install.sh --target /path/to/your/repo --config framework.config.yaml --dry-run

# 3. Install for real
bash install.sh --target /path/to/your/repo --config framework.config.yaml

# 4. Read the generated CLAUDE.md and IMPLEMENTATION_GUIDE.md, then start your first
#    governed session.

Full walkthrough — including the recommended phased rollout so you don't drop 24 hooks on a team at once — is in IMPLEMENTATION_GUIDE.md.

Design principles (the ones that make it portable)

  • Mechanical over advisory. If a rule matters, a hook enforces it. Docs that aren't enforced are aspirations.
  • One source of truth, rendered everywhere. State lives in one machine-readable file; dashboards/plans are generated, never hand-edited. Drift is designed out, not chased.
  • Tiered autonomy. Most work is auto-approved; only high-blast-radius changes block on a human. The tier boundaries are config, not code.
  • Adversarial self-review for recursive changes. When a change edits the governance system itself, it must survive an independent critic before landing.
  • Capture the lesson, not the event. Knowledge notes record why something was non-obvious, so the next agent doesn't relearn it.
  • Adapters, not forks. Language/stack specifics live in swappable adapters. The constitution and process never depend on a language.

Versioning & support

Keel is versioned independently (see VERSION / CHANGELOG.md). Adopting teams pin a version and pull updates deliberately. Local tweaks live in your repo; framework upgrades are a diff you review — never an overwrite of your customizations.

See IMPLEMENTATION_GUIDE.md for the upgrade workflow.
